What IMS does

The Incident Management System is the tool Rangers use during the event to keep track of what's happening on-playa. When a Ranger calls something in on the radio, Dispatch logs it as an incident in IMS, assigns Rangers to respond, updates its status as the situation evolves, and closes it out when resolved. The same system handles field reports (write-ups of things Rangers saw or did) and visits (the structured intake when a guest comes to Sanctuary).

What you can do in it

Log incidents in real time

Create an incident from a radio call: priority, what happened, where on the grid, summary. Move it through the dispatch lifecycle (new → dispatched → on scene → closed) as the response unfolds.

Write field reports

Document things you saw or did that didn't need an immediate response, or that you want on the record. Field reports can stand alone or attach to an incident.

Run Sanctuary visits

Track guest interactions at the Ranger shelter: arrival, what resources Rangers provided (rest, clothes, food, water), and departure. Each visit is a structured intake, not freeform notes.

Pinpoint on the BRC grid

Locations use the way Rangers actually navigate: concentric street (Esplanade, Alfa, Bravo…) crossed with clock position (e.g. 9:30). Optional name and details round it out — "Camp Questionmark, near the main stage".

Tag who responded

Attach Ranger callsigns to incidents and visits, with an optional role description. Useful for after-action review and for the audit log.

Add photos & files

Any incident, field report, or visit can carry attachments — photos of a scene, scans of paperwork, whatever's relevant.

See updates live

When someone in HQ creates or updates an incident, every other connected IMS screen reflects it within seconds — no page refresh. That's how Dispatch keeps a shared view of the night.

Search history

Browse and filter all incidents for the current event, or pull up past events. Find your historical involvement by callsign for shift handoffs or end-of-event review.

Print clean

Pages have a dedicated print mode that hides buttons and form widgets, leaving just readable content. Useful for shift handoff packets or as off-grid backup.

How it knows who you are

You log in with the same email and password as Clubhouse — there's no separate IMS account. On login IMS reaches into Clubhouse and reads:

  • Your callsign — used everywhere in IMS
  • Your Ranger positions (Dispatcher, Driver, etc.) — these can grant per-event permissions
  • Your team memberships — same idea
  • Whether you're currently on duty (you have an open timesheet entry in Clubhouse)
  • Whether you're on-site at the event

This means changes you make in Clubhouse propagate. Get a new position approved there, you'll see the matching IMS permissions on your next login. Change your callsign, IMS picks it up the next time its in-memory directory cache refreshes (every five minutes by default).

Who can see what

Permissions are configured per event by IMS admins. Each event (e.g. "2026") carries its own access rules. Rules can target:

  • A specific Ranger by callsign
  • Everyone with a given position in Clubhouse — e.g. "anyone with the Dispatcher position can write incidents"
  • Everyone on a given team
  • Anyone currently on duty in a specific position
  • Everyone authenticated (the wildcard *) — common for read access

Each rule grants one mode: read, write, report (write own field reports only), or write_visits. Rules can also be scoped to apply only while a Ranger is on-playa.

Where the data lives

Everything is stored in databases operated by the Rangers' tech volunteers — not shared with BMORG, vendors, or external analytics. Incidents, field reports, and visits live there; attachments live in either a Ranger-owned object store or local disk depending on the deployment. An audit log records every authenticated change for the historical record of how the event was managed.

One-line mental model (helpful for engineers too): IMS owns events, incidents, places, streets, visits, field reports, and the audit log in its own database. It treats people as a read-only feed from a separate system called Clubhouse. Almost every design decision in the rest of this doc flows from that split.

End of the Ranger-facing overview. Everything below is engineering reference — architecture diagrams, schema, API endpoints, deployment notes. Rangers can stop reading here. The technical sections live in the same page because the same mental model applies; they just go deeper.

Domain workflow

When does a Ranger create an Incident vs. a Field Report vs. a Visit?

IMS has three top-level objects that look similar in the schema — each has its own table, each has report entries, each can have Rangers attached. They serve different roles:

Incident

Something happened that needs response. Tracked through a state machine, has a priority, can have Rangers dispatched to it.

Field Report

A Ranger writes up something they saw or did. May or may not be attached to an incident. Async record-keeping.

Visit

A guest interaction at Sanctuary (Rangers' guest shelter): arrival, resources provided, departure. Can attach to an incident if it grew out of one.

Incident lifecycle

The five states an Incident can be in, and the transitions you'll see in practice.

INCIDENT.STATE is an enum: new, on_hold, dispatched, on_scene, closed. The schema enforces enum membership but not transition rules — the API will let you write to any state from any other. The diagram below shows the conventional flow:

stateDiagram-v2 [*] --> new : Ranger reports new --> dispatched : Rangers assigned new --> on_hold : Defer new --> closed : False alarm / resolved on intake dispatched --> on_scene : Rangers arrive dispatched --> on_hold : Resources reassigned dispatched --> closed : Resolved en route on_scene --> closed : Situation resolved on_scene --> on_hold : Pause & reassess on_hold --> new : Re-triage on_hold --> dispatched : Resume closed --> [*]

Priority

INCIDENT.PRIORITY is a tinyint with five conventional values. The schema doesn't enforce them — these are operator convention:

ValueMeaningTypical use
1HighestLife-safety, structure fire, missing child, unresponsive person
2HighMedical, assault, vehicle accident, propane leak
3NormalDefault for most reports — disputes, lost person, sound complaint
4LowNoise after quiet hours, minor MOOP, illegal vending
5LowestLost & found, deferred follow-ups

The seed data exercises all five values across the example 2026 incidents.

Location grid

How the LOCATION_* columns on INCIDENT encode a point in Black Rock City.

BRC is a partial-circle city. The Man is at the center; the streets fan out from him in a 2/3 horseshoe, with the open mouth pointing north toward the Temple and deep playa. Locations are encoded with three columns that together form a polar coordinate:

ColumnMeaningExample
LOCATION_CONCENTRICReference into CONCENTRIC_STREET.ID — the lettered ring (Esplanade, Alfa, Bravo, …)"2" (= Bravo, per the seed)
LOCATION_RADIAL_HOURClock hour, 2 through 109
LOCATION_RADIAL_MINUTEClock minute (0, 15, 30, 45)30
LOCATION_NAMEOptional human-readable name"Camp Questionmark"
LOCATION_ADDRESSOptional free-form address—
LOCATION_DESCRIPTIONOptional further detail"Near the main stage area"

What the seeded incident would look like in JSON

{
  "event": 1,
  "number": 3,
  "summary": "Lost participant near sound camps",
  "location": {
    "name": "Camp Questionmark",
    "concentric": "2",
    "radial_hour": 9,
    "radial_minute": 30,
    "description": "Near the main stage area"
  },
  ...
}

The string "2" is the CONCENTRIC_STREET.ID for Bravo in event 2026. Each event has its own concentric-street naming (the schema lets the 2026 event use Alfa/Bravo/… while a different event uses Arcade/Ballyhoo/…), which is why LOCATION_CONCENTRIC is an FK against (EVENT, ID) not a global ID.

Clubhouse database

External system, read-only from IMS's perspective. Schema lives at directory/schema/current.sql; IMS only reads a tiny subset of the full Clubhouse model.

Less than 10% of Clubhouse's surface is used. The real person table has ~70 columns (addresses, phone, SMS verification, T-shirt sizes, emergency contacts, behavioral agreements, BPGUID, SFUID, …). IMS reads just id, callsign, email, status, on_site, password — and even status is filtered to a small whitelist.

Status whitelist (who can log in)

IMS only loads persons whose Clubhouse status is one of:

active · inactive · inactive extension · auditor · prospective · alpha

Excluded statuses (cannot log in, cannot be attached to incidents): bonked, echelon, deceased, dismissed, past prospective, resigned, retired, suspended, uberbonked.

On-duty detection

"On duty" means: a timesheet row exists for the person with off_duty IS NULL and on_duty within the last 60 days. The current on-duty position is one input into the onduty: matcher in event access rules.

Login flow

How an HTTP session becomes a known user.

sequenceDiagram autonumber participant U as Browser participant W as IMS web
(/ims/auth) participant US as UserStore
(in-proc cache) participant CH as Clubhouse DB participant K as JWT signer U->>W: POST /ims/api/auth { email, password } W->>US: lookup user by email alt cache stale US->>CH: SELECT id, callsign, email, status, on_site, password FROM person … US->>CH: SELECT positions, teams, timesheet … CH-->>US: rows US-->>US: rebuild cache (TTL = 5 min default) end US-->>W: User { handle, email, status, on_site, password-hash, positions, teams, on-duty } W->>W: argon2id verify(submitted, stored hash) alt verified W->>K: mint access + refresh tokens
(carry handle, positions, teams, on-site, on-duty) K-->>W: signed JWTs W-->>U: 200 + Set-Cookie else mismatch W-->>U: 401 end

Three things to note about this flow:

  • Login uses email, not callsign. The callsign is used everywhere else, but the login form expects an email address.
  • Password hashes are stored on the Clubhouse side using argon2id with shared parameters (lib/argon2id.ClubhouseParams). IMS never writes them.
  • Tokens snapshot Clubhouse state at login. Positions, team membership, on-duty status, and on-site flag are baked into the JWT claims. They don't re-query Clubhouse on every request. Refreshing the token also refreshes those claims.

Authorization model

Who can do what, decided per request.

Authorization is layered. Global roles are coarse-grained and come from config. Event-level roles are fine-grained and come from rows in EVENT_ACCESS.

Global roles

RoleGranted byGets
AnyAuthenticatedUserSuccessful loginList events · read incident types · read personnel · read streets
AdministratorPerson's PERSON.IS_ADMIN flag is setAdminister events · streets · incident types · places · debugging

Event-level roles (from EVENT_ACCESS.MODE)

RoleMode valueCan do
EventReaderreadRead incidents and all field reports for the event
EventWriterwriteFull read/write on incidents and field reports
EventReporterreportWrite own field reports only (no incident access)
EventVisitWriterwrite_visitsRead/write visits only

How a user matches an access rule

For each EVENT_ACCESS row of a given event, IMS checks whether the user matches the EXPRESSION. The matchers are mutually exclusive prefixes:

ExpressionMatches if…
*Always (any authenticated user)
person:HardwareUser's callsign equals Hardware (case-sensitive)
position:DispatcherUser has the Dispatcher position in Clubhouse
team:Driving TeamUser is a member of that team
onduty:DispatcherUser is currently signed in as Dispatcher (open timesheet row)

Additionally, VALIDITY = 'onsite' rules only apply when person.on_site = true at login time. EXPIRES can render a rule inert past a timestamp.

Common dev tasks

TaskCommand
Bring stack updocker compose -f docker-compose.dev.yml up -d
Tail logsdocker logs -f ranger-ims-go
Reseed Clubhouse DBStop stack · rm -rf .docker/mysql/data-clubhouse · up
Hash a passworddocker run --rm -v $PWD:/src -w /src --entrypoint sh ims-go-air -c 'go run . hash_password --password XYZ'
Open a SQL shell in IMS DBdocker exec -it ranger-ims-db mariadb -uims -pims ims
Open a SQL shell in Clubhouse DBdocker exec -it ranger-clubhouse-db mariadb -uclubhouseuser -pclubhousepassword rangers
Reload Caddy after Caddyfile editdocker compose up -d --force-recreate --no-deps caddy recreate

Note on the last row: Caddy's bind-mounted Caddyfile binds a specific inode at container creation. Atomic file editors (vim, IDE save) change the inode, so the container keeps reading the old file. Recreating the container re-resolves the mount.
